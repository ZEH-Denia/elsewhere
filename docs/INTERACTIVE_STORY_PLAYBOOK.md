# 互动叙事网页开发手册

这套方法适合互动故事、多结局短篇和带选择的创意网页。以《Elsewhere：未接来电》为例，先做一段陌生玩家能独立玩完的体验，再扩写分支、统一美术、打磨交互，最后按同一个构建版本验收和发布。

## 1. 开工前写一页创作简报

| 要决定的事 | 要写到什么程度 | 《未接来电》的例子 |
| --- | --- | --- |
| 一句话体验 | 写清谁进入什么处境、要做什么、会看到什么结果 | 接起平行世界自己的电话，做两次选择，看到另一种人生的得失 |
| 完整体验 | 用一行列出从进入到收束的动作，标明第一次选择在哪里 | 开始 → 接听 → 对话 → 两次选择 → 结局 → 重听或继续 |
| 选择的意义 | 写出每个选项的代价、即时回应、后续变化与结局差异 | 一次选择决定如何看待当下，另一次决定接下来做什么 |
| 首版范围 | 写明优先设备、最少场景数、体验时长目标和本轮收束点 | 优先桌面浏览器，先交付一通完整来电，验证后再扩职业线 |
| 视觉方向 | 选一张代表性参考图，定光色、构图和文字出现的位置 | 暖色工程桌与冷色排练室，用同一场雨把两个空间连起来 |
| 发布条件 | 记下目标平台、访问要求、发布人和交付材料 | 可匿名访问的作品链接、可复验的发布版本、独立准备的作品介绍与截图 |

先用灰盒读一遍剧本。记下玩家第一次获得关键信息、第一次做决定、第一次获得回报分别用了多久。读完结局，让试玩者回答「我做了什么，最后哪里变了」。这个回答比预先设计多少张背景更能说明核心玩法是否成立。

## 2. 从一条可玩路径逐步扩展

| 阶段 | 做什么 | 做到这里才进入下一阶段 |
| --- | --- | --- |
| 01 灰盒样片 | 用占位图和真实台词接通一条线路，让一次选择带来两种可区分的结果，并能回到入口 | 新玩家能自己开始、读懂问题、选择和结束 |
| 02 分支闭环 | 补齐所有选项、即时反馈、分支结局及重听。先画路径表，再把它写成数据 | 每组选择抵达对应结局。删掉一个结局或绕过必经选择时，校验会失败 |
| 03 视觉样片 | 用真实界面分别验一张首页、一张对话、一张选择或结局画面 | 参考样片的构图、文字对比和操作位置获确认，才批量做场景 |
| 04 内容扩展 | 沿用同一套对白、选择、结局和信件结构，加其他线路与收束 | 新线路都能从真实入口进入、完成并返回。每封信或结局有自己的内容 |
| 05 试玩打磨 | 从空白浏览器试玩，修复看不懂、找不到、点不动、点太多和无法恢复的问题 | 首访和回访都能走通，主要交互在实际浏览器里复验 |
| 06 交付 | 从确认的提交构建，在生产预览走通后更新目标站点，再用匿名窗口复验 | 证据能对应源码提交、线上资源和实际试玩结果 |

上线是硬性要求时，灰盒阶段就试一次目标平台的预览或上传能力，确认域名、静态路径和权限流程。内容和素材可以继续迭代，发布环境的限制越早发现越容易处理。

## 3. 项目骨架与状态规则

纯浏览器叙事可从 **React + TypeScript + Vite** 起步，界面样式用 CSS，有团队习惯再加 Tailwind。剧本与素材随项目发布，本机进度可用 `localStorage`。当需求出现跨设备续玩、多人协作或需要服务端保管的数据时，再设计账号和后端。

```text
src/App.tsx             组织页面、进入与返回
src/story/              剧情数据、状态转换、结局规则、存档校验
src/components/         对白、选项、信件、场景与热点
src/index.css           颜色、间距、焦点和动效
public/backgrounds/     同源图片文件和回退素材
tests/                  剧情组合、异常路径与存档用例
docs/                   产品简报、视觉规则和剧本定稿
tasks/current.md        当前要交付的范围与验收条件
tasks/reviews/          对应提交的验收结果
```

1. **给剧本稳定 ID。** 每个节点、选项、场景、结局和信件都用独立 ID。改台词、换图和调整文案顺序时，存档仍能找到原来的剧情位置。
2. **让一次选择产生一次状态更新。** 用清楚的规则处理继续、选择、重听、退出和读信。记录当前节点、已选项和解锁状态。悬停或 Tab 聚焦产生的画面预览只属于界面状态，选项确认后才写入剧情。
3. **按完整路径校验。** 从起点用真实推进规则跑每组选择，检查是否经过必经节点、抵达匹配结局并解锁对应来信。加入缺目标、错误映射、绕过选择和死循环的反例。《未接来电》曾出现「图中有结局」却漏报「某个选择组合到不了结局」的情况。 [首通分支复审](../tasks/reviews/TASK-003.md#2026-11-19-最终复审pass)
4. **先定存档语义。** 明确「刷新」「续玩」「重听」「重新开始」分别保留什么。存档按结局 ID 或信件 ID 保存多次结果，读取时核验结构和 ID。为旧版、损坏存档、存储受限留出恢复入口。重新开始要让玩家看到将清除的范围并确认。

写分支表时，每行填写「选择组合 → 必经场景 → 预期结局 → 附带结果」。例如「承认遗憾 + 为音乐留时间 → 两次选择各自的反馈 → 把旋律找回来 → 可重听」。剧本编辑、代码实现和验收可使用同一张表。 [《未接来电》的四条路径](STORY_BRANCHES.md)

## 4. 场景、界面与音效怎么做

- **先定样片，再做素材表。** 每张图列出对应节点、叙事作用、关键道具、裁切安全区、文字覆盖区和回退资源。生成或绘制时保持同组色温、镜头及材质，给不同阶段不同的叙事焦点。成图放进页面检视实际裁切和对比度。《未接来电》先确认雨夜首页，再重绘 43 张后续插画，最后重新对准热点。 [插画验收与实际提示词](../tasks/reviews/TASK-003.md#2026-11-21-后续场景插画重绘pass)
- **让主操作跟着玩家的注意力。** 接听放进来电卡，提问与答案放在同一阅读区，结局按钮写清下一步。需要文字衬底时，用局部渐层和文字颜色维持可读性，检查实际会生效的布局。 [桌面走查与返修](../tasks/reviews/TASK-003.md#2026-11-21-桌面自主走查与返修pass)
- **让画面可以逐步增强。** 加载当前场景，只预取紧邻的画面。新图准备好后再淡化替换，加载失败用回退图或上一帧。可选的推镜和视差只用在关键情节。画面切换期间保持按钮可用，在动效被打断、资源缺失或开启减少动态效果时仍能推进。 [场景推镜验收](../tasks/reviews/TASK-003.md#2026-11-22-场景推镜与视差pass)
- **热点描述属于故事，光环属于提示。** 圆心固定在道具上，用轻微呼吸光环引导，悬停或聚焦时停稳。给热点可读名称，用 Tab 到达，用 Enter 或 Space 打开，Escape 关闭。音效放在接通、收束等有意义的动作上，随用户操作触发，提供可记忆的静音开关。 [体验与热点验收](../tasks/reviews/TASK-003.md#2026-11-22-七项桌面体验改进复验pass)

## 5. 真实问题和可复用解法

| 现象 | 处理方法 | 怎么确认解决了 |
| --- | --- | --- |
| 首页底部像突然出现一块白板 | 从画面向文字区过渡成深色渐层，把颜色写进共享样式 | 打开玩家实际使用的布局，再检查标题、按钮和焦点可见性 |
| 点了半天还没到第一次选择 | 合并同一轮短问答，保留戏剧停顿与实质信息。给重听提供直达分岔的入口 | 用真实点击重新计数。《未接来电》的医生线由约 19 次降到 8 次 |
| 看见了结局，不知道下一步 | 按钮写成具体动作，例如「接听更多来电」。在入口旁说明解锁条件 | 用空白浏览器走到结局，观察第一次试玩的人能否继续 |
| 连点切句选中文字，下一次点击失效 | 处理对白区重复按下，只抑制误选。保留手动拖选与按钮本身的动作 | 分别做双击、三连点、下一次独立单击和拖选后的点击 |
| 切到选择反馈，键盘焦点丢失 | 把焦点送到反馈标题或继续按钮，关闭弹层时送回原触发控件 | 只用 Tab、Enter、Space 和 Escape 走完选择、反馈、退出和重回页面 |
| 背景缺失后白屏，热点落在错图上 | 等解码成功才替换。依次尝试回退图和上一有效画面，按实际显示的背景决定是否显示热点 | 分别让主图失败、主图与回退图都失败，再进入下一场景检查恢复 |
| 同一职业重玩以后只能找到一封信 | 用来信或结局 ID 记录每封结果，在总机提供重读；尾声引用确实读过的细节 | 同一职业走两个结局，刷新后重读两封，并检查尾声回应 |
| 后台显示发布成功，评委仍可能看到登录页或旧版 | 独立验证匿名访问、入口的 JS/CSS 文件名和关键资源内容，再从公网试玩 | 记录源码提交、入口引用、资源比对和匿名试玩。平台注入水印时比较底层静态资源 |

案例依据见 [TASK-003 审查记录](../tasks/reviews/TASK-003.md)。表中的点击次数来自这次作品，下一部作品应按自己的阅读节奏设目标。

## 6. 验收、协作与发布

| 检查层 | 实际要看到的结果 | 留下什么 |
| --- | --- | --- |
| 剧情 | 每组选择、必经节点、结局、信件和解锁对得上，异常数据能退出或恢复 | 路径表、正例和反例结果 |
| 工程 | 按项目的锁文件安装，类型检查、已有测试和生产构建通过 | 提交号、实际命令和结果 |
| 浏览器 | 用生产构建实点首访、重听、刷新续玩和明确重开。核对鼠标、键盘、快点、图片失败、降低动效和目标视口 | 浏览器、视口、实际走过的路径、截图和未覆盖项 |
| 公网 | 同一个已验收的构建完成部署，无登录的访问者能打开并完成核心流程 | 线上 URL、发布记录、入口资源和匿名试玩结果 |

《未接来电》的本地检查顺序是 `npm ci` → `npm run typecheck` → `npm run test:story` → `npm run build` → `npm run preview`。新项目沿用这个顺序，命令以自己的 `package.json` 为准。 [本地运行说明](../README.md#本地运行)

用 `tasks/current.md` 写当前可交付的一件事，让一个人或一个代理负责写入，设计与验收反馈都回到同一个任务。每次交付带上基线、改了哪些文件、实际检查、已知缺口和提交号。通过写 `PASS`，有可复现的问题写 `FIX` 并沿用编号，缺环境或决策写 `BLOCKED`。用户侧的画面和操作以生产预览为准。

发布时从确认的提交构建，备好可回退的上一个版本。把代码同步、验收、上线、赛事投稿分别登记到实际完成的步骤，保留对应证据。若要参赛，在开工时就看官方对开发工具、托管、署名和过程材料的要求，再定团队分工。持续保存可公开的真实过程截图，作品说明按实际实现和发布记录撰写。 [协作协议](COLLABORATION.md) · [公开发布验收](../tasks/reviews/TASK-003.md#2026-11-23-qoder-sites-公开版本更新pass)

## 7. 下次可以直接复制的任务模板

```text
作品一句话
给［玩家］一段［情境］，让他们通过［核心动作］看到［具体结果］。

这轮交付
在［目标设备］从［入口］走到［可核验的结果］。
请用［剧情定稿或路径表］、［已确定的视觉参考］和［当前基线］。

状态和边界
［每种选择的即时反馈、到达的结局、重听/刷新/重开的规则］。
［这轮允许修改的范围，以及确认过的发布方式］。

验收
列出每组选择的预期结局。用［鼠标和键盘］实际走通入口至收束。
复现［一个本轮最可能出现的异常］并验证恢复。
记下实际浏览器、视口、路径、构建和提交号。
```

第一次用这套方法时，可以把任务填成「1280×720 下从首页接听一通电话，做一次选择，到达两个可区分的结局，并能重听」。先用占位图试玩，再用真实剧本决定需要哪些画面。等这段体验成立，扩展时就有一条可对照的完整基线。
